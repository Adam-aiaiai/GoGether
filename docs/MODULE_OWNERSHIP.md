# 五人分工与并行开发约定

更新：2026-11-18。以本文件作为当前 A–E 分工。任务完成情况以代码和验证记录为准。

## 已确认范围

账户与个人资料；活动发现；活动发布、编辑及取消；报名与候补；集合、二维码签到与反馈；我的活动及历史。

两个特色：
- 新手参与信息：经验要求、入门指导、自带物品、备用器材名称与数量。器材只展示，借用请提前沟通。
- 活动问答：登录用户无须报名即可提问、回答，采用问题加一层回答。组织者标记由活动所有者决定。

活动结束或取消后停止新增问答，保留阅读和作者删除。删除问题时整条问答从列表移除；删除回答只移除该回答。新回答只提醒提问者，自己的回答不提醒自己。通知第一阶段采用 App 内收件箱。

## 五人主责

每人负责所属页面、业务逻辑、数据接入、权限、必要测试和接入说明。预计工作量按新增内容、规则难度和联调评估，首轮联调后按实际进度调整。

| 成员 | 主责与接续入口 | 必须交付 | 独立开发输入 |
| --- | --- | --- | --- |
| A：账号、资料与个人活动 | `feature/auth`、`feature/profile`、`MyEventsScreen.kt`、公共导航 | 注册登录、退出和会话恢复；昵称与兴趣编辑；已报名/候补中/我创建的活动；历史与参与记录；统一身份入口 | 测试用户、各种报名状态、历史活动、签到和反馈记录 |
| B：活动发布与发现 | `feature/event`、`feature/explore`、活动管理页容器 | 创建、编辑、取消；起止及截止时间；搜索筛选；新手信息与器材展示；详情和管理页整体布局 | 测试组织者、活动列表、其他模块的模拟组件 |
| C：报名与候补 | `feature/registration`、报名数据实现、名单组件 | 报名/取消、人数、候补顺序、补位、截止约束、名单；重复及跨设备名额一致性；转正通知记录 | 空位、满员、截止、取消活动和多个测试身份 |
| D：问答、公告与消息 | 新建问答模块、公告、从个人页独立的通知组件 | 提问回答、组织者标记、内容管理、关闭后禁止写入；公告、回复通知、收件箱、已读 | 组织者、正式成员、未报名者、示例问答和通知 |
| E：集合、签到与反馈 | `feature/checkin`、签到/反馈数据实现 | 集合信息、地图入口；签到开关、二维码扫描和校验；出席名单；结束后评分评论和重复检查 | 正式成员、候补者、未报名者、有效/失效凭据、历史活动 |

A 负责个人活动展示，C 负责报名规则。D 提供通知组件，A 在个人页接入。E 读取 B 保存的集合地点。

## 公共维护与文件边界

| 公共事项 | 维护人 | 边界 |
| --- | --- | --- |
| 环境、工程配置、Application 注入、导航、模块接入 | A | 建立公共入口，各成员完成自己的数据操作和权限 |
| 活动模型、详情/管理页容器、公共主题与样式 | B | 接入其他人已验证的组件，各人修改自己的页面 |
| 报名模型、一致性、跨模块报名规则核对 | C | 集中处理报名，不承接全组后端 |
| 问答、公告、通知模型及收件/已读接口 | D | 统一通知格式，业务负责人决定何时产生通知 |
| 签到/反馈模型、两设备完整流程检查协调 | E | 记录问题，各负责人修复自己的问题 |

`GogetherRepository.kt`、`AppSnapshot` 和共用字段有多个调用方。调整接口先明确输入、输出、失败情况和迁移方式，再由维护人接入；模拟实现与正式实现使用同一契约。

活动详情和管理页由 B 维护容器：C 提供报名和名单，D 提供问答/公告，E 提供签到/出席。个人页及个人活动由 A 维护，D 提供通知。组件独立实现，避免同时修改整个页面。

## 跨模块操作

| 操作 | 端到端负责人 | 配合 |
| --- | --- | --- |
| 发布活动并为组织者占位 | B | C 核对报名约束 |
| 编辑时间和容量 | B | C 核对已有报名，E 使用更新后的条件 |
| 取消整场活动 | B | 一致更新活动、报名、取消通知；C 核对，D/E 根据状态限制操作 |
| 退出报名及补位 | C | 补位和通知记录尽量在同一事务完成，D 读取展示 |
| 提问、回答、回复提醒 | D | 使用 A 的身份和 B 的活动状态 |
| 签到和反馈 | E | 执行时验证身份、活动、报名资格及重复记录 |

沿用：组织者占一席；截止后停止报名和补位，开始前仍可取消报名；结束按统一状态/时间判断。正式数据操作由可信后端核验权限与时间。当前反馈规则：已结束活动的正式报名者每人一次，不要求签到，包含组织者。规则改变需同步调用方。

## 并行开发起点

1. 同步公共基线，五人均能运行 Demo。分支建议：`feat/member-a-account`、`feat/member-b-events`、`feat/member-c-registration`、`feat/member-d-discussion`、`feat/member-e-attendance`。
2. 每人定义自己的模型和接口，A 协调接入。小范围拆分混合代码，保留已开展的成员改动及运行流程。
3. 共用测试用户及空位/满员/候补/取消/结束活动。模块可独立测试，应用共用一个状态来源。
4. 先通过模拟实现推进，再接入统一真实服务。未配置服务时明确展示开发模式。

截至本次更新，团队尚未提供共用 Firebase 配置。A 先交付可接入版本；后续全组连接同一项目，各模块分别完成持久化、同步和权限。

## 合并与验收

每完成一段可运行功能就提交小改动，合并前同步主线，保留其他成员字段和入口。A/B/C 尽早联通真实身份—活动—报名—我的活动，D/E 同时通过模拟接口推进。

| 成员 | 最少验证 |
| --- | --- |
| A | 会话恢复、资料保存、切换身份隔离、个人活动分类 |
| B | 字段校验、组织者权限、编辑/取消、新手信息及筛选 |
| C | 最后一席并发、重复请求、补位、截止及取消边界 |
| D | 未报名问答、内容权限、回复提醒、已读隔离、关闭后禁止新增 |
| E | 有效/失效二维码、报名资格、重复签到、出席记录、反馈资格 |

真实服务就绪后以两个账号、两台设备检查同步，重启验证保存。各自测试计入个人任务，联合验证预留时间。功能稳定后共同确定 UI，B 维护主题，A–E 修改自己的页面。

个人贡献以实际提交、测试及团队协商记录，分工表不等同于已完成工作或贡献比例。
